1. GENERACIÓN Y MANEJO DEL ESP32_ID (esp32_id_manager.py)

Flujo detallado:
- Durante el primer arranque del ESP32, ESP32IdManager verifica si existe 'esp32_id.json'
- Si no existe, genera un ID único de 8 caracteres alfanuméricos en mayúsculas combinando:
  * MAC address del ESP32 (usando machine.unique_id())
  * Timestamp del RTC (para esto debería estar actualizado con la hora de internet correspondiente a GMT -5, sino se puede actualizar que no continúe con el programa e indique el error por BLE, para que de esta manera el usuario pueda saber qué fue mal en el lado de la APP)
  * Formato: {mac}_{timestamp}
- Guarda el ID en 'esp32_id.json'
- En arranques posteriores, siempre lee el ID del archivo
- Este ID NUNCA cambia durante toda la vida del dispositivo, por lo que si no existe el ID guardado en el archivo 'esp32_id.json' entonces consultará en la BD por la MAC dentro de /hdd-monitor/esp32/registered/{esp32_id} y lo comparará con su MAC, si coincide cargará el nombre del documento como esp32_id permanente de nuevo.


2. SISTEMA DE REINTENTOS (wifi_manager.py)
Parámetros de control:
- CONNECTION_TIMEOUT = 20000 (20 segundos por intento)
- RETRY_INTERVAL = 5000 (5 segundos entre reintentos)
- MAX_RETRIES = 3 (intentos máximos)

Proceso detallado:
a) Primer nivel de reintentos (connect_wifi):
   - Intenta conectar
   - Espera 20 segundos máximo
   - Si falla, retorna mensaje

b) Segundo nivel (ensure_wifi_connected):
   - Hace 3 intentos máximo
   - Entre cada intento espera 5 segundos
   - Incrementa reconnection_attempts
   - Registra last_disconnect_reason


3. PROCESO DE ARRANQUE DETALLADO:
a) Inicialización (Orden exacto):
   1. ESP32 bootea -> boot.py (si existe) -> main.py
   2. Inicialización de managers en orden:
      - ESP32IdManager (primero para tener ID disponible)
      - WiFiManager
      - WatchdogManager (timeout 120 segundos)
      - SystemManager
      - RelayManager
      - PerformanceMonitor
      - ConnectionMonitor
      - MQTTManager

b) Verificación de Configuración:
   1. Busca wifi_config.json
   2. Busca panel_config.json
   3. Si falta alguno, entra a modo configuración

c) Modo Configuración Bluetooth:
   1. Activa BLE con nombre "ESP32-{ID único del ESP32}"
   2. Configura servicio UART BLE
   3. Buffer de recepción: 4096 bytes
   4. Espera datos JSON con formato:
      {START}{"ssid":"xxx","password":"xxx"}{END}
   5. Timeout de espera: 300 segundos


4. MANEJO DE ESTADOS Y ERRORES:
Estados del Sistema:
- INITIAL: Arrancando
- WIFI_CONFIG: Configurando WiFi vía BLE
- MQTT_CONFIG: Configurando panel vía MQTT
- RUNNING: Operación normal
- ERROR: Estado de error
- UPDATING: Actualizando firmware

Manejo de Errores:
a) WiFi:
   - Desconexiones
   - Credenciales inválidas
   - Timeout de conexión
   - Red no encontrada

b) MQTT:
   - Cola de mensajes pendientes
   - Reintentos de conexión

c) Sistema:
   - GC (Garbage Collection) cada 5 minutos
   - Monitoreo de memoria libre


5. MONITOREO Y MÉTRICAS:
a) Métricas de Sistema:
   - Memoria libre/usada
   - Tiempo de ejecución
   - Conteo de reinicios
   - Causa del último reinicio

b) Métricas de Conexión:
   - Estado WiFi
   - Fuerza de señal (RSSI)
   - Intentos de reconexión
   - Última razón de desconexión

c) Métricas de Relés:
   - Estado actual
   - Último cambio
   - Historial de cambios (últimos 50)
   - Eventos pendientes


6. SINCRONIZACIÓN DE TIEMPO:
Proceso:
1. Intenta obtener hora de worldtimeapi.org
2. Si falla, intenta con timeapi.io
3. Si ambos fallan, usa RTC interno
4. Actualiza cada 5 minutos (TIME_SYNC_INTERVAL = 300000)


7. PERSISTENCIA DE DATOS:
Archivos críticos:
- esp32_id.json: ID único del dispositivo
- wifi_config.json: Configuración WiFi
- panel_config.json: Configuración del panel
- boot_count.txt: Contador de reinicios
- update_status.json: Estado de actualizaciones


8. GESTIÓN DE MEMORIA:
- Monitoreo constante del uso de memoria
- Garbage collection proactivo
- Umbrales de memoria libre/usada
- Prevención de fragmentación

Todo esto funciona en conjunto para garantizar que el sistema:

Nunca deje de monitorear los relés
Mantenga la comunicación MQTT
Se recupere de fallos automáticamente
Preserve la integridad de los datos

Tópico de configuración específico para cada ESP32, basado en su ID único. El ESP32 se suscribe a este tópico durante la configuración para recibir su configuración específica de panel.
En el tópico de operación. Es específico para cada panel según su clientId y panelId, que se reciben en la configuración a través del tópico de configuración. El ESP32 se suscribe a este tópico después de recibir su configuración y lo utiliza para publicar sus mensajes de estado y recibir comando de pasar a modo de configuración.
El ESP32 publica cada 30min estadísticas del sistema en este tópico, que también es específico para cada dispositivo según su ID; este también funciona para indicar que el ESP32 está en línea, si no se detectara en línea por más de 30min entonces la VM (google cloud virtual machine corriendo una función intermediaria entre broker mqtt y la BD en firestore) debería cambiar el campo status de CONFIG a OFFLINE. También el ESP32 publica alertas del sistema en este tópico.




Después de recibir y aplicar la configuración, el ESP32 publica un mensaje de confirmación en el Tópico de configuración con el estado "config_applied".
Después de publicar este mensaje, el ESP32 se desuscribe del Tópico de configuración, ya que no necesita recibir más mensajes de configuración en este punto.
El ESP32 se reinicia para iniciar con un estado limpio y aplicar la nueva configuración.
Después del reinicio, en start_normal_operation, el ESP32 se suscribe a su tópico de operación y comienza su operación normal.
Si en algún momento el ESP32 necesita volver al modo de configuración, recibiría un comando específico en su tópico de operación. Al recibir este comando, el ESP32 se desuscribiría del tópico de operación y volvería a suscribirse al tópico de configuración para recibir una nueva configuración.
Después de recibir y aplicar la nueva configuración, el ESP32 repetiría los pasos 1-5, desuscribiéndose del tópico de configuración, reiniciando, y volviendo a su tópico de operación.



VM detecte si es que hay un nuevo esp32_id dentro del tópico de configuración para que tome ese esp32_id y lo registre en /hdd-monitor/esp32/registered/, por ejemplo /hdd-monitor/esp32/registered/EK2748293 que tiene campos MAC (del esp32 usando machine.unique_id()), IP, status (si es que esta CONFIG o sea en modo configuración, RUNNING o sea modo de operación normal u OFFLINE el esp32), client_id, panel_id (panel contra incendios que estará monitoreando) y location. Luego cuando el ESP32 ya esté asignado a un cliente, la VM se encargará de colocar el id del cliente a que pertenece y su ubicación.

una vez que la APP haya detectado el nuevo ESP32 en la BD creado por ejemplo con:
MAC: la mac del esp32
status: CONFIG (o sea en modo configuración)
client_id: null
panel_id: null
location: null
IP: null

y que la APP le haya asignado cliente, nombre de panel y ubicación, rellenando esos campos y quedando el documento del esp32 por ejemplo en:
MAC: la mac del esp32
status: RUNNING (o sea modo de operación normal)
client_id: Boticas MiSalud
panel_id: Panel Sótano 1
location: Sótano 1
IP: 192.168.18.23

la VM debe detectar ese nuevo cambio y postearlo en el Tópico de configuración, luego que el ESP32 detecte ese nuevo mensaje y continúe con su configuración hasta pasar al modo de trabajo normal asignado a un cliente y panel.
